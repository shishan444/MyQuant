## 第一档：语义正确性类（建议优先偿还）

### TD-01 仓位口径披露对加仓行用错公式（orders_capped 计数可能虚高）

- 位置：`core/backtest/engine.py` 的 `_position_sizing_disclosure`（约 :1384-1484，risk_budget 档重放循环）
- 问题是什么：这个函数给每条验证记录计算 `position_sizing` 披露（含 orders_capped 截断计数）。它的重放逻辑对**所有入场行**（包括加仓行）统一用「风险预算公式」重放期望下单量。但引擎的实际行为是：只有首仓走风险预算公式，**加仓行走的是独立的 add_fraction 百分比路径**（`engine.py:1342`，`add_value = c.value_now × add_fractions[col]`，没有档位分支）。
- 为什么是问题：两套公式算出的「计划下单量」不同。用错公式去对照实际成交量，会把「正常足额的加仓」误判成「被截断的加仓」——orders_capped 计数可能虚高。这和线一修掉的 CARD-01（trace_resolver 的 capped 推导同族错位）是同一个根因的另一个面：线一只修了 resolver 侧（vr_signal_trace 表的 capped 列），这个披露侧（result_json 里的 position_sighting.orders_capped）没动。
- 处置建议：单独一个小 change，把重放循环按行类型分派公式——首仓行用风险预算公式、加仓行用 add_fraction 公式。修法与 CARD-01 完全同构，可参考 `trace_resolver.py` 的 `_expected_qty` 按码分派写法。

### TD-02 库内持久化 JSON 裸解析约 20+ 处（损坏行会炸裸 500）

- 位置：全域分布。已坐实的五处：`core/persistence/repository/research.py:761`（decision_json 已随线三退役消解）与 `:773-774`（equity timestamps/values 两处）、`api/routes/research/validation_detail.py:47-50`（params/result 两处）、`core/analysis/validation_service.py` 多处、`hypothesis_service.py` 等
- 问题是什么：工程有成文纪律（`core/analysis/errors.py:29-59` 的 `load_stored_json`）：库内 JSON 列解析必须走结构化通道，数据损坏时返回 422 带 `RESEARCH_STORED_DATA_INVALID` 错误码、带行级定位信息，禁止裸 `json.loads` 把 `JSONDecodeError` 直接穿出去炸 500。但全库实际有 20 多处仍然裸调用 `json.loads`。
- 为什么是问题：库内行如果被外部改写、迁移截断或写入中断弄坏，这些裸解析点会抛裸异常——用户看到的是无信息量的 500，不知道哪条记录坏了、哪个字段坏了，也没法结构化处理。线二的 CARD-10 修掉了本分支新增的 gene_hits 一处（一行改动+行级定位），证明修法成熟。
- 处置建议：一个专项 change 全域收敛。每处改走 `load_stored_json`（带 source 点名与行定位 detail），一处约一到三行，改动机械、可批量。

### TD-03 同一语义两种颜色（verdict 样式映射三处两口径）

- 位置：`web/src/components/validationRecords/RecordBrowser.tsx:143-145`（VERDICT_BADGE）与 `RecordDetail.tsx:35-36`（VERDICT_COLOR）一致（inconclusive=金色）；`web/src/pages/Workbench.tsx:31-33` 漂移（inconclusive=灰色）
- 问题是什么：「证据不足」这一判定结论，在验证记录页的两个组件里渲染成金色，在工作台页渲染成灰色。三处各自维护 verdict 到颜色/徽标的映射表，没有单源。
- 为什么是问题：颜色是判定的视觉语言。同一结论两处两色，用户会当成两种不同的状态；后续每加一个 verdict 展示点就多一份拷贝，漂移只会扩大。
- 处置建议：把 verdict→样式映射收敛进一个共享模块（前端已有 `traceSemantics.ts` 这类纯函数层先例），三处消费同一份。Workbench 在本次 diff 外，属跨页面改动，随下一个前端 change 顺手做即可。

## 第二档：行为边界类（有意识的接受，登记防沉默存续）

### TD-04 MTF 策略层内被清洗的信号不落留痕表（CARD-03 裁决方向 A）

- 位置：`core/strategy/executor.py:758-760`（层内加仓抑制清洗）与 `:766`（层内同 bar 互斥清洗）——这两个清洗点产出的吞没事实，在 MTF 路径（多周期组合）下没有收集进 `SignalSet.swallowed`
- 问题是什么：验证信号留痕（线一建设）承诺「每个信号事实落盘」。现状是：单周期策略的两类求值层清洗（同 bar 进出场互斥吞进场、加仓抑制吞加仓）都会落 vr_signal_trace 表；但走 MTF 组合路径的策略，**层内**发生的这两类清洗没有收集点——只有跨层组合后的冲突面有收集。这是实现忠实设计卡的结果（设计卡 §2.6 只写了单周期生产点），不是实施走样。
- 为什么接受（方向 A 裁决理由）：补齐需要先裁决层轴到执行轴的投影语义（一个 1d 层的清洗事件映射到哪几根 4h bar）、层内面与组合面的去重规则——这是独立的产品行为定义，塞进修复队列会扩大原 change 边界。接受边界的代价：MTF 策略的信号回溯页签会少一类「为什么没成交」的解释行。
- 处置建议：独立 change 补齐（设计卡修订+投影语义裁决+spec 增场景）。防沉默存续三件已落实：本条登记、代码注释披露（executor.py 层函数注释）、原 change 呈批记录在案。

### TD-05 显式段 label 无值域校验（SEC-1）

- 位置：`core/analysis/validation_service.py` `_validate_explicit_segments`（label 仅 `str()` 强转）→ 落 `exec_ref` 列 → detail 端点整份回显
- 问题是什么：分段验证的显式段清单由调用方提交，label 字段没有任何长度上限与字符集校验，直接落库并在 detail 响应里整份回显（该端点不分页）。
- 为什么是问题：超长 label（数 MB）会同时放大存储与响应；当前是本地单用户系统暴露面有限，但该端点是 HTTP 面，一旦进入局域网暴露就可被单请求打满。修复是一行参数级改动。
- 处置建议：`Field(max_length=64)` 加可见字符集校验，超限 `RESEARCH_PARAM_INVALID` 拒绝（B4 既有明细链同面一并覆盖）。随任一触碰该文件的机会带上。

### TD-06 q 搜索参数无长度上限（S-1）

- 位置：`api/routes/research/records_list.py:68` `q: Optional[str] = Query(None)`
- 问题是什么：搜索关键词参数没有长度限制，超长搜索词触发无索引的全表逐行 LIKE 模式匹配。
- 为什么是问题：与 TD-05 同理——廉价的资源放大面。修复同样是一行：`Query(None, max_length=200)`。
- 处置建议：与 TD-05 同批处理。

## 第四档：流程教训类（方法论，防止再犯）

### TD-14 生成物再生成必须同批修全部消费方

- 事实：retire-verify-sessions（2026-11-02）退役后端端点时**没有同批再生成 openapi.json**，生成物保持陈旧——前端手写类型层的引用一直「看起来有效」。线二 B1 按义务再生成后，退役 schema 正确消失，暴露 33 个 tsc 基线错误（win_rate 可空族/结构化 subject/Verify 会话类型链），被迫临时建冻结文件（`generated-verify-frozen.ts`）承载旧消费方。
- 教训：退役类 change 的「生成物同批再生成」义务必须包含「消费方同批适配」，否则陈旧生成物会掩盖破坏直到下一次再生成引爆。冻结文件是 F4 债（旧 verify 会话前端 hooks 退役）的承载物，F4 执行时一并删除。

### TD-15 git add 前必须核对工作区每个文件归属

- 事实：线三实施时，某队友在工作区留下的未提交实验改动（把一个测试文件整体重写成另一文件的副本）被 lead 的 `git add` 误夹带进提交 0bff5d0——reviewer-3 审查时抓到（八类迁移断言面全丢+违反「删改清单非静默」纪律），回滚修复为 3 行最小 diff 后 amend。
- 教训：多 agent 协作共享工作区时，提交前 `git status` 逐文件核对归属是硬纪律；`git add` 用显式文件清单（本例实际用了清单但清单里含了被污染文件——清单本身要从「我改了什么」的自觉出发而非目录猜测）。

### TD-16 测试构造形制必须对齐生产实况

- 事实：线二泛化查询的 P0 缺陷（裸串 parent_ids 必炸 500）被绿测试掩护了整整一轮——测试构造全用 `json.dumps([hid])`（合法 JSON 数组形），而生产库 542 行 parent_ids 是 100% 裸串（合法 JSON 为 0 行）。形制倒置使 `json_extract` 在测试库里永不抛错。
- 教训：凡是测试要覆盖「库内已有数据」的行为，构造数据的形制必须先实查生产库值域分布（一次 `SELECT COUNT(*) ... GROUP BY json_valid(col)` 级别的探查），不能凭「规范形制」直觉写 fixture。

### TD-17 COALESCE 求值顺序陷阱（SQLite 专项）

- 事实：`coalesce(json_extract(col,'$[0]'), case when json_valid(col)=0 then col end)` 的意图是「合法 JSON 取首元素、裸串取自身」，但 SQLite 的 COALESCE **必须先求值第一参数**——`json_extract` 对裸串求值即抛 `malformed JSON`，兜底分支永远不可达。正确形是先验 `json_valid` 的 CASE。
- 教训：全库同族组合（`coalesce+json_extract` 跨行）需用多行模式检索（`rg -U`），按行 grep 会漏。已修三处（CARD-21），无其他残留（已全域检索确认）。
